#+title: Chirp user guide
#+options: toc:2 num:nil

* Sign in

~M-x chirp-login~ opens a supported browser at ~https://x.com~ using
browser-session's shared persistent profile.  Chirp imports only the
~auth_token~ and ~ct0~ cookies into ~chirp-x-auth-file~
(~(locate-user-emacs-file "chirp/auth.json")~, mode ~0600~).

Ordinary commands then use that private auth file.  Run
~M-x chirp-login~ again only to refresh an expired session or switch
accounts.  Chirp never reads a browser cookie database, copied
headers, ~CHIRP_X_AUTH_TOKEN~, ~CHIRP_X_CT0~, or ~auth-source~.
~M-x chirp-forget-browser-session~ deletes the auth file without
signing out of the browser.

Configure ~browser-session-browser~, ~browser-session-profile-directory~,
~browser-session-profile-root~, and proxy settings once for all consumers.
Chirp no longer creates its own browser profile; old profile directories are
left untouched. Set ~CHIRP_X_BEARER_TOKEN~ only if X rotates its public web token.

After a definitive stale-query error, Chirp refreshes read-operation
query IDs from the current ~TwitterInternalAPIDocument~ registry.
Retry the failed read, or run ~M-x chirp-refresh-query-ids~.
~chirp-x-query-id-overrides~ remains authoritative.  Write-operation
IDs are never selected from the dynamic cache or retried.

Direct messages require the optional source-built Rust module.  Follow
[[file:../native/README.org][native module build instructions]] and set
~chirp-xchat-native-module-file~ to its absolute path.  Other Chirp
features remain usable when it is absent.

* Entry points

Start with ~M-x chirp-home~ or ~M-x chirp-following~ for the primary timelines,
or ~M-x chirp-direct-messages~ for the XChat inbox.  The
[[file:../lisp/chirp-transient.el::(transient-define-prefix chirp-dispatch][application menu]] also opens bookmarks, likes, profiles, lists, search,
saved drafts and scheduled posts.

Commands that accept a post or list ID intentionally do not parse URLs. Use ~M-x chirp-open-url~ for a supported X or Twitter URL.

To route those links from ~browse-url~:

#+begin_src emacs-lisp
(add-to-list 'browse-url-handlers
             (cons chirp-url-browse-regexp #'chirp-open-url))
#+end_src

* Direct messages

** Session and synchronization

~M-x chirp-direct-messages~ performs one user-confirmed XChat unlock, then opens a recent-conversation inbox with participant avatars, latest-message previews, compact local times, and request or muted status trails.  ~RET~ or mouse-1 opens the current row.  ~M-x chirp-dm-cancel-unlock~ cancels active recovery and reports an uncertain outcome.

While the Chirp application remains active, one Appkit-owned XChat websocket receives bounded binary events, updates canonical conversations and open inboxes immediately, decrypts new messages for open conversations, sends the official keepalive, and reconnects after transport closure without retrying writes.  Conversation facts are shared across fresh views; each buffer keeps its own history window, position, reply context, and draft.

** Message interactions

Conversations decode signature-verified plain text through Appkit's semantic
markup codec, and the composer encodes the same plain codec before native
encryption.  Verified reactions appear beneath their target message, not as
separate rows; the account's own reactions have a distinct chosen style.
Replies keep a view-local context card above the composer.

The [[file:../lisp/chirp-dm-conversation.el::(appkit-bindings-define 'chirp-dm-conversation--timeline-mode-map][message actions]] and
[[file:../lisp/chirp-dm-conversation.el::(appkit-bindings-define 'chirp-dm-conversation--mode-map][composer actions]] use [[file:../../appkit.el/appkit-bindings.el::(defconst appkit-binding-defaults][Appkit's native/Evil bindings]].
On the timeline, Return activates local content, such as an attachment or
embedded post; ordinary text keeps point, draft and modal state unchanged.
In input, Return sends the captured draft.  Newline, reply, reaction and
attachment staging remain separate actions.  Native and Evil states share
these semantics.

** Attachments

*** Incoming attachments

Chirp downloads encrypted attachment bytes from X's TON media service and asks the native module to decrypt them with the exact verified conversation-key version named by the message.  Images, GIFs, and SVGs render inline.  Videos, audio, and documents expose native Emacs actions; attached posts render as Chirp tweet cards; other links remain explicit URL actions.

Decrypted files use ~chirp-cache-directory~, like other Chirp media.  Protect or clear that directory according to the local machine's confidentiality requirements.

*** Outgoing attachments

The attachment chooser offers typed staging actions.  File attachment infers
photo, GIF, video, audio or document from native byte detection, not the
filename; clipboard attachment accepts local files or PNG/JPEG/BMP bytes.
A universal prefix forces a document, and the chooser also has an explicit
file action.  Staging does not send.  Photos and GIFs keep inline previews;
other kinds use typed cards.

Private clipboard sources survive captured sends and failure, and are removed
after acknowledgment, draft removal or buffer shutdown.  Ordinary user files
are never deleted.  Rebuild the native module when updating this interface.

On send, the native module validates and encrypts each file under the conversation's latest verified key.  Chirp then initializes the upload, sends bounded encrypted parts to TON, finalizes it, and encrypts the message envelope under the same key version.  Uploads use the browser session already captured by ~chirp-login~; no separate media credential is required.  Temporary ciphertext is removed after success, failure, or cancellation.

** Delivery guarantees

Direct-message reads never send read acknowledgments.  Text, replies, reactions, and attachments are never retried or inserted optimistically.  Reply context and every composer object remain until X returns a validated acknowledgement.

* Browsing and composing

The [[file:../lisp/chirp-core.el::(defvar-keymap chirp-view-mode-map][view keymap]] contains Chirp-specific controls; its
[[file:../lisp/chirp-core.el::(appkit-bindings-define 'chirp-view-mode-map][semantic actions]] share the Appkit theme.  The
[[file:../lisp/chirp-core.el::(defun chirp--setup-evil][Evil adapter]] adds modal browsing controls without replacing native
search or visual motions.  Customize shared keys through
[[file:../../appkit.el/appkit-bindings.el::(defcustom appkit-binding-overrides][appkit-binding-overrides]] and inspect the effective binding with ~C-h k~
at the relevant buffer position and state.

** Timelines

~chirp-home~ and ~chirp-following~ share one primary buffer but retain
independent posts, pagination, pending new posts and positions.  Switching
subviews restores that state without fetching again; closing the window
does not discard it.

While visible, the active feed checks for new posts according to
~chirp-timeline-poll-interval~.  Refreshing checks immediately without moving
the current row.  Fresh posts wait behind the clickable ~Show N posts~
header-line button until explicitly revealed.

Approaching the visible bottom loads the next older page without moving the
current row.  ~chirp-timeline-auto-load-threshold~ sets the character distance;
nil disables automatic pagination, not explicit loading.

The [[file:../lisp/chirp-transient.el::(transient-define-prefix chirp-transient-tweet-operate][post menu]] operates on the current tweet or quote.  Local links and media
have their own actions; reply and other writes remain subject to X's
permissions.

~Follow~ / ~Following~ updates only the matching profile summary or user-list
row after X confirms the action.  Loaded posts, pagination, and the reading
position stay intact; failed requests leave the displayed relationship unchanged.

** Compose

The [[file:../lisp/chirp-actions.el::(defvar-keymap chirp-compose-mode-map][compose keymap]] defines draft-specific controls, while
[[file:../lisp/chirp-actions.el::(appkit-bindings-define 'chirp-compose-mode-map][shared compose actions]] provide attachment staging, submission and
cancellation.  The [[file:../lisp/chirp-transient.el::(transient-define-prefix chirp-transient-compose][draft-options menu]] edits live content without publishing.

A public draft may contain several committed parts and one editable input.
Return on a committed row loads that exact part for editing; Return in input
inserts a newline.  Neither publishes.  Explicit submission retains the draft
until X acknowledges it; cancellation stops an in-flight submit or closes an
idle composer.  Saving an unsent X draft and scheduling publication are
separate commands.

Click ~Audience~ on a post or quote, or use draft options, to choose who
can reply.  Attachments support up to four images or one MP4, with alt text
edited before publication.  Video uploads show progress in the status strip.

JPEG, PNG, and WebP attachments may be at most 5 MiB; GIFs 15 MiB;
MP4 videos 512 MiB, uploaded in 1 MiB chunks.  Premium accounts can
exceed the standard 280 weighted-character limit.

Attachment commands only stage drafts.  Public posts have no generic-document
kind: document-forcing prefixes and unsupported BMP images are rejected
without changing the draft.  Clipboard URI files remain user-owned; private
pixel sources live until removal, cancellation or confirmed publication.

* Notifications and translation

#+begin_src emacs-lisp
(chirp-notifications-mode 1)
(setq chirp-notifications-interval 300
      chirp-notifications-max-results 20
      appkit-translate-target-language "zh")
#+end_src

The first check establishes a baseline.  Later checks run every five
minutes by default.  Linux uses freedesktop notifications; macOS uses
AppleScript.

The post menu translates the selected tweet or quote below its unchanged
original.  Chirp uses X's translation endpoint with a 120-second deadline.
HTML entities such as ~&amp;~ are decoded once, after all response chunks have
been joined.  To use the optional, separately authenticated Respond backend:

#+begin_src emacs-lisp
(setq chirp-translation-backend-function #'appkit-translate-respond-backend)
#+end_src

The target language is shared through ~appkit-translate-target-language~;
there is no automatic backend fallback.

* Thread reply filtering

Chirp hides likely spam replies with a conservative default list.
Matching ignores case and never filters the focus tweet or its ancestor chain.
The view's spam-rule action saves a literal phrase from the current reply;
a universal prefix starts from its display name.
~M-x chirp-thread-edit-spam-rules~ edits the file under ~user-emacs-directory~.

#+begin_src emacs-lisp
(setq chirp-spam-rules nil) ; disable filtering
#+end_src

To propose shared rules upstream, use the
[[https://github.com/LuciusChen/chirp/issues/new?template=spam-rule.yml][upstream spam rule submission form]].

* Media

** Timeline presentation

Images render as row-sliced previews.  Normal non-condensed posts—including
timelines, reposts, thread focuses, and thread replies—share one large carousel
display.  Quoted posts and other condensed cards retain X Web's center-cropped
~TweetPhotos~ grid.

Chirp owns X's aspect-ratio and crop policy, media resource resolution, and
post/profile actions.  Appkit owns the sliced grid executor, mounted track
selection, image hotspots, composite Canvas and playback lifetime.  Cached
rendered content is immutable; inserting it twice creates independent tracks.

Source aspect ratios determine the common carousel height.  Each item occupies
at most 80 percent of the reference width, 4-pixel gutters separate items, and
constrained boxes use center cover.  Static carousels use SVG.  Inline video
playback replaces the complete composite scene with one Canvas while preserving
the same geometry and keeping ~window-hscroll~ at zero.

** Actions

The [[file:../../appkit.el/appkit-media-track.el::(defvar appkit-media-track-map][Appkit track action map]] owns carousel navigation and inline controls.
Selecting another item retargets those local actions; they never control the
previous inline occurrence.  Activation toggles inline video or opens a still
image in the reader.  Clicking a hotspot selects that item without moving
the text cursor.

Dedicated viewing and external playback are explicit alternatives to inline
activation.  Opening an additional presentation frame leaves the host view
visible and does not start paused media; closing it changes no other window.
Looping applies only to an initialized, seekable source and does not start
playback.  Space remains available to the user's global key configuration.

Touch drags on headings, cards, image hotspots and inline transport controls
scroll the host buffer; only completed taps activate them.  Card borders and
indentation are display-only, so copied text keeps neither and text entity
offsets remain aligned.

** Dedicated viewer

The dedicated buffer uses video.el's reader model.  Chirp does not override
~video-display-buffer-function~: the default placement is the selected window,
while users may globally choose another window or a presentation frame.

Cold-cache photos are acquired asynchronously before the reader opens.  The
request belongs to the exact Chirp source buffer: closing that buffer,
replacing its feed, or canceling pending reader navigation prevents a late
download from opening another viewer.

The buffer presents the current source; every window displaying it owns an
independent absolute scale and viewport origin.  A video's Appkit session may
also retain the same player for an inline surface.  The virtual media plane may
be much larger than the window, while its Canvas and native raster stay exactly
viewport-sized.  Fit commands calculate a scale once, so later window resizing
does not resize the media.

Images and videos support zoom, unrestricted pan, fit, mouse-wheel input and
middle-button dragging.  Videos additionally expose playback transport.
Source navigation moves through the carousel.  Quitting an ordinary reader
returns to the saved Chirp view; quitting an independent presentation frame
closes only that frame.

Returning to the same window with unchanged layout leaves the inline media
track intact: playback continues, or remains paused, with its mute state
unchanged. Actual source-width or text-scale changes still reflow the source
rows; preserving inline playback through that reflow is not yet supported.

Appkit owns each activated video's canonical resource, stable cache identity,
and persistent-cache policy; video.el owns the playback session, player, and
inline/dedicated presentation leases.  Chirp records the active inline
presentation against its containing entry, so every dedicated-media action
reuses the same player even after point leaves the media hot spot.  The reader
preserves the exact position, play/pause and canonical mute state, buffered
ranges, and in-flight sparse network cache without issuing a second media
request.  Closing either video presentation leaves the other lease running;
closing the last lease lets video.el retire the player and any incomplete
session cache.  Closing the owning Chirp source also closes its managed
dedicated reader.  Explicit external playback and download remain separate.

** Configuration

#+begin_src emacs-lisp
(setq chirp-media-thumbnail-size 256
      chirp-video-player-window-size '(1280 . 720)
      chirp-media-download-directory "~/Downloads/chirp/"
      chirp-media-prefetch-images nil
      chirp-backend-read-cache-ttl 15)
#+end_src

Set ~chirp-video-player-command~ to another player, or ~nil~ to open externally
requested videos in the browser.

* Primary timeline ownership

Home and Following retain separate in-session page state while sharing one
Surface.  Its reducer owns page transitions, request generations, cursors,
pending posts and semantic reading positions.  App-level entity updates may
refresh tweet contents without taking ownership of pagination.

Initial, refresh and older-page reads are managed Effects.  Transport
callbacks only settle gates; typed terminal messages must still match the
exact feed state and request generation.  Switching feeds or closing the
Surface revokes delivery authority before physical cancellation.

Media prefetch and quote enrichment use a fixed-purpose post-commit Effect
bound to the original App and exact feed owner.  Its deferred start keeps
synchronous cache hits outside an active Loop pass.  Switching or closing
cancels pending starts; already shared acquisitions retain their own
lifetimes.  Collection/search controllers and the DM websocket service have
separate lifecycles, not the primary timeline's reducer/Effect contract.
